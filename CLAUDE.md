# CLAUDE.md

Guidance for Claude when working in this repository.

## What this project is

An applied data science project: probabilistic hourly demand forecasting plus the capacity-commitment decision it supports. The U.S. grid (EIA-930) is the case study; the framing must stay general so a reader from any industry understands it.

**The deliverable is a decision and the evidence for it**, not a leaderboard. Lead with the business question and the answer, then the method.

## Working agreement with the owner

- The owner writes and must understand the code. Explain, review, suggest, and test; do not write whole modules unprompted. When asked for code, keep it small and explain it.
- Never invent data, results, or performance numbers. If something has not been run, say so.
- Verify data availability and facts against the source before relying on them. Mark unverified claims as such.
- Prefer simple, defensible models. No deep learning, LLMs, or dashboards for show.
- A negative result (the operator forecast is hard to beat) is acceptable if it is measured honestly.
- Keep scope tight; extensions go in `docs/project_brief.md`, not in the code.

## Methodology rules (do not break)

1. **No leakage.** Splits are time-ordered. Features use only information available at forecast issue time. Actual weather is look-ahead for a day-ahead forecast; label it as an upper bound or use forecast weather.
2. **Untouched test period.** Never tune on it.
3. **Fair comparison with the operator forecast.** Same target, same hours, same information set. Establish the issue time before claiming a win.
4. **Pre-set balancing-authority selection** based on data completeness only, written down before modeling.
5. **Target definition.** Reported `Demand (MW)` is the default target. Never train and score on imputed values. Document any alternative.
6. **Time handling.** Order by UTC. Use local time only for calendar features. Check daylight-saving duplicates and gaps.
7. **Costs are assumptions.** Always show results across a sweep of the shortfall/surplus ratio.
8. **Uncertainty.** Report block-bootstrap intervals for headline comparisons.
9. **Report per balancing authority**, not just pooled averages.

## Code conventions

- Python >= 3.11. Project structure is added only when the work needs it; keep the repo minimal.
- Anything a conclusion depends on must be reproducible from code in the repo, not only from a notebook.
- Raw and derived data are git-ignored; never commit them.
